# Phase 3 开放问题与默认决策

Phase 3 目标是把系统接入企业 IT 生态：SSO、多通道通知、病毒扫描、自助转交、开放 API 和 Webhook。根据当前“无需再确认，后续自行确认”的执行约束，本文件直接记录默认决策，后续实现按这些决策推进。

## OQ-14：SSO 选哪家提供方

**默认决策：先做通用 OAuth2/OIDC 配置提供方。**

理由：

- 不依赖企业微信、钉钉、Azure AD 的真实租户和密钥，能在本地和 CI 中完整测试。
- 企业微信、钉钉和 Azure AD 后续可作为 provider profile 接入同一抽象层。
- 自建 OAuth2/OIDC 是 roadmap 候选之一，适合先把账号绑定、回调、安全校验和审计打通。

实现要求：

- Provider 配置来自环境变量和数据库配置，测试中使用 fake provider。
- 支持授权地址、token 地址、userinfo 地址、client_id、client_secret、scope、redirect_uri。
- state 必须进 Redis，带 TTL，防 CSRF 和重放。

## OQ-15：SSO 自动账号创建策略

**默认决策：仅允许已有账号登录，不自动创建账号。**

理由：

- 当前系统有严格角色和部门权限，自动创建容易产生越权和待分配账号。
- 管理员可以先建用户，再由用户绑定 SSO。

实现要求：

- 首次 SSO 回调按 verified email 或已存在绑定查找本地账号。
- 找不到账号时拒绝登录，返回清晰错误。
- 绑定和解绑写审计日志。

## OQ-16：是否同时支持本地账号 + SSO

**默认决策：支持双轨，但 admin 可设置用户必须使用 SSO。**

实现要求：

- 默认用户可使用本地密码或 SSO。
- 用户级字段控制是否强制 SSO。
- 强制 SSO 后，本地密码登录返回业务错误。
- admin 可在用户管理页切换策略。

## OQ-17：开放 API 的限流粒度

**默认决策：API Key 为主，IP 为辅。**

实现要求：

- 每个 API Key 默认 1000 次/小时。
- Redis key 以 `external_api:{key_id}:{hour}` 计数。
- 同时保留 IP 级别保护，防止单 Key 被集中滥用。

## OQ-18：Webhook 失败重试策略

**默认决策：失败重试 5 次，指数退避，最终进入死信表并通知 admin。**

实现要求：

- 重试延迟：1m、5m、15m、1h、6h。
- 每次推送带 HMAC 签名和事件 ID。
- 接收方返回 2xx 视为成功；其他状态码或超时进入重试。
- 死信记录可在后台查询并手动重放。

## 其他默认边界

- 企业微信和钉钉 Phase 3 先支持机器人/Webhook 通道，不做通讯录同步。
- SMTP 邮件使用 Jinja2 模板，退订只针对外部邮件通道，不影响站内通知。
- ClamAV 扫描为异步，上传成功不代表扫描通过；扫描中状态需在文档列表显示。
- 开放 API 首批只读，不提供外部写入能力。
