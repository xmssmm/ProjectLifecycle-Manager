# 项目管理系统 V2 流程驱动改造规格

**日期**：2026-05-13  
**适用范围**：项目管理系统 V2 流程修复与体验改造  
**输入材料**：

- `docs/项目管理系统V2问题汇总报告(1).md`
- `docs/step by step.txt`

**核验说明**：本文件是流程设计初稿。问题真实性和实施优先级以
`docs/V2_ISSUE_VALIDATION_REPORT.md` 为准；后续实施计划应先剔除已实现项，
避免把已有后端能力当作全新功能重复开发。

---

## 1. 背景与核心判断

V2 测试暴露的问题不应被理解为零散功能缺口。根因是系统已经具备若干功能模块，但用户在真实业务中需要的是一条清晰、有先后顺序、有角色职责、有关口校验、有金额联动的完整流程。

本次改造的目标不是简单补齐 17 个问题，而是把系统从“模块堆叠”调整为“流程驱动”：

1. 主项目先立项、审核，审核通过后才承载子项目。
2. 子项目先创建、审核，审核通过后自动生成标准环节。
3. 核心执行环节必须按顺序推进，每一关都有必传材料和业务校验。
4. 财务付款和后评价是灵活环节，不强制卡在主线顺序中，但必须计入完成条件。
5. 分步验收必须支持多人、分步骤、分材料确认，全部完成后才能完成验收环节。
6. 付款成功后金额应实时联动到子项目和主项目。
7. 页面应展示用户可理解的信息，不应要求用户手动输入后台 UUID。

## 2. 设计原则

### 2.1 先流程，后模块

所有页面、按钮、接口和校验都围绕“下一步该做什么”组织。用户进入一个项目后，应能明确看到当前状态、缺什么材料、谁来操作、完成后流向哪里。

### 2.2 后端守规则，前端给引导

前端负责把流程讲清楚、把选择项做成下拉、把按钮显示在合适位置；后端负责最终状态校验、权限校验、材料校验和金额联动，不能只依赖前端控制。

### 2.3 状态变化必须可追溯

主项目审核、子项目审核、环节推进、验收步骤完成、付款、结项都应写入审计或操作记录，避免业务上出现“状态为什么变了”无法解释。

### 2.4 业务字段对用户友好

页面默认展示名称、标题、金额、角色、状态、时间等业务语言。UUID 只作为技术标识保留在详情或管理场景中，不作为普通用户填写项。

## 3. 角色与职责

| 角色 | 核心职责 |
| --- | --- |
| 综合部负责人 | 创建或审核主项目，审核子项目，监督预算和结项 |
| 项目负责人 | 创建子项目，上传环节材料，推进项目，发起验收和后评价 |
| 项目参与人员 | 参与采购、合同、验收等具体环节操作 |
| 验收负责人 | 按验收步骤上传证明材料并确认完成 |
| 财务负责人 | 录入付款、上传付款凭证，处理付款红冲 |
| 管理员 | 维护部门、用户、权限、流程模板和基础数据 |

## 4. 端到端主流程

### 4.1 第一阶段：主项目创建与审核

1. 综合部负责人创建主项目。
2. 创建表单填写：项目名称、责任部门、总预算、预计完成时间、备注。
3. 责任部门通过部门下拉选择，不允许手动填写部门 UUID。
4. 保存后主项目状态为 `待审核`。
5. 审核人在审核页检查预算、部门、时间等信息。
6. 审核可通过、驳回，也可在审核时修正允许修正的字段后通过。
7. 审核通过后状态变为 `未开始`，此时允许创建子项目。

### 4.2 第二阶段：子项目创建与审核

1. 项目负责人创建子项目。
2. 创建表单填写：关联主项目、项目名称、责任部门、预算、计划完成日期、负责人、参与人员。
3. 子项目预算提交时校验不能破坏主项目预算约束。
4. 保存或提交后状态为 `待审核`。
5. 综合部负责人审核子项目，可在审核时修正预算等允许字段。
6. 审核通过后状态变为 `未开始`。
7. 系统自动生成 6 个标准环节：立项、采购、合同签订、验收、财务付款、后评价。

### 4.3 第三阶段：核心执行环节按顺序推进

核心执行环节包括立项、采购、合同签订、验收。它们必须按顺序过关：

| 顺序 | 环节 | 推进前置条件 |
| --- | --- | --- |
| 1 | 立项 | 必传会议资料、会议纪要等立项材料 |
| 2 | 采购 | 必传 OA 采购申请截图；若为询价类，必须上传 3 家供应商报价单 |
| 3 | 合同签订 | 必传主合同；可上传补充协议 |
| 4 | 验收 | 普通验收需验收报告；分步验收需所有验收步骤完成 |

页面规则：

1. 环节详情页必须明确显示当前环节、前置环节状态、必传材料、已上传材料、缺失材料。
2. 当必传材料和业务校验满足时显示“推进环节”按钮。
3. 当不满足推进条件时隐藏或禁用按钮，并显示原因。
4. 推进操作由后端再次校验，避免绕过前端。

### 4.4 第四阶段：分步验收

验收环节支持两种模式：

| 模式 | 适用场景 | 完成条件 |
| --- | --- | --- |
| 普通验收 | 一次性验收 | 上传验收报告后推进 |
| 分步验收 | 多批次、多人员、多证明材料 | 所有验收步骤均完成后推进 |

分步验收规则：

1. 验收环节提供“启用分步验收”开关。
2. 启用后可新增验收步骤。
3. 每个步骤包含：步骤序号、步骤名称、责任人、计划日期、说明、状态。
4. 每个步骤必须能关联上传的验收材料或证明材料。
5. 步骤责任人必须是子项目负责人或参与成员。
6. 步骤完成前必须至少上传一份对应验收材料。
7. 所有步骤完成后，验收环节才允许推进完成。

### 4.5 第五阶段：财务付款与金额联动

财务付款不强制卡在立项、采购、合同、验收主线顺序中，但必须纳入子项目最终完成条件。

付款规则：

1. 财务负责人可录入多笔付款。
2. 每笔付款必须包含金额、付款日期、付款说明和付款凭证。
3. 付款支持预付款、尾款等多次付款场景。
4. 付款成功后自动重算子项目 `spent_amount`。
5. 子项目 `spent_amount` 变化后自动重算主项目 `spent_amount`。
6. 付款红冲后同样触发金额重算。
7. 金额字段只通过付款服务层联动，不允许前端或普通项目编辑直接修改。

展示规则：

1. 主项目列表和详情显示总预算、已用金额、剩余金额。
2. 子项目列表和详情显示预算、已用金额、剩余金额。
3. 看板和报表使用同一套金额口径。

### 4.6 第六阶段：后评价、子项目完成与主项目结项

1. 后评价环节可在核心执行后进行，需上传后评价报告和经济效益评价报告。
2. 子项目所有必做项完成后，系统将子项目标记为 `已完成` 或允许申请结项。
3. 子项目结项前应校验：核心环节完成、验收完成、付款记录满足业务要求、后评价完成。
4. 主项目下所有子项目完成或结项后，综合部负责人可将主项目变更为 `已结项`。
5. 主项目结项页展示所有子项目完成状态、预算、已用金额和汇总金额。

## 5. 状态模型

### 5.1 主项目状态

| 状态 | 含义 | 可执行动作 |
| --- | --- | --- |
| 待审核 | 已创建，等待审核 | 审核、驳回 |
| 驳回 | 审核未通过 | 修改后重新提交 |
| 未开始 | 审核通过，等待拆解子项目 | 创建子项目 |
| 进行中 | 存在进行中的子项目 | 查看进度、管理子项目 |
| 已完成 | 子项目均完成，等待结项 | 申请或执行结项 |
| 已结项 | 主项目正式归档 | 查看、归档、报表 |

### 5.2 子项目状态

| 状态 | 含义 | 可执行动作 |
| --- | --- | --- |
| 待审核 | 已创建，等待审核 | 审核、驳回 |
| 驳回 | 审核未通过 | 修改后重新提交 |
| 未开始 | 审核通过，环节已生成 | 启动或推进第一环节 |
| 进行中 | 环节执行中 | 上传材料、推进环节、付款、后评价 |
| 已完成 | 所有必做项完成 | 申请结项 |
| 已结项 | 子项目关闭 | 查看、归档、报表 |

### 5.3 环节状态

| 状态 | 含义 |
| --- | --- |
| 未开始 | 前置环节未完成或尚未启动 |
| 进行中 | 当前可操作环节 |
| 已完成 | 材料和校验均满足，已推进完成 |

## 6. 页面与交互改造

### 6.1 部门选择与展示

需要改造的页面：

1. 用户编辑页：部门字段改为下拉选择。
2. 主项目创建和编辑页：部门字段改为“责任部门”下拉。
3. 子项目创建和编辑页：部门字段改为“责任部门”下拉。
4. 主项目列表、详情、审核页：优先展示部门名称，必要时辅助展示部门 ID。
5. 部门管理页：显示部门 ID，便于管理员排查数据问题。

### 6.2 主项目页面

列表页应展示：

1. 项目编号、项目名称、责任部门、状态。
2. 总预算、已用金额、剩余金额。
3. 创建人、创建时间。
4. 操作入口：详情、编辑、审核、创建子项目。

详情页应展示：

1. 主项目信息和状态。
2. 子项目列表和汇总。
3. 已用金额实时汇总。
4. 下一步操作建议。

### 6.3 子项目页面

列表页应支持：

1. “我负责的”筛选。
2. “我参与的”筛选。
3. 状态、主项目、责任部门筛选。

创建页应提供流程引导：

1. 说明子项目必须关联已审核通过的主项目。
2. 说明审核通过后会自动生成 6 大环节。
3. 说明预算会纳入主项目预算约束。

详情页应成为流程工作台：

1. 顶部显示当前子项目状态和下一步。
2. 中部显示 6 大环节进度。
3. 当前环节突出展示必传材料和推进按钮。
4. 财务付款、后评价作为独立但必做区域展示。

### 6.4 环节详情页

环节详情页应包含：

1. 当前环节名称、状态、顺序。
2. 前置环节完成情况。
3. 必传材料清单。
4. 已上传材料清单，显示 `display_name`，不显示系统文件名作为主标题。
5. 缺失材料提示。
6. 满足条件时显示“推进环节”按钮。

### 6.5 采购环节

采购环节新增采购类型：

| 类型 | 规则 |
| --- | --- |
| 询价类 | 必须上传 3 家供应商报价单 |
| 招标类 | 按招标材料规则校验 |
| 单一来源 | 按单一来源说明和审批材料校验 |

V2 首批必须落地询价类 3 家报价强制校验。招标类和单一来源可先完成字段、下拉和基础材料提示，复杂规则可在后续版本扩展。

## 7. 后端改造规格

### 7.1 部门字段

1. 项目、用户相关读模型应补充部门名称。
2. 列表接口支持返回 `dept_name` 或嵌套部门摘要。
3. 写接口继续接收 `dept_id`，但前端通过下拉获取，不要求用户手填。

### 7.2 主项目金额与创建信息

1. 主项目模型保留 `spent_amount`。
2. 主项目列表和详情接口必须返回 `spent_amount`、`creator_id`、`creator_name`、`created_at`。
3. `spent_amount` 由子项目已用金额汇总得出。
4. 修复任何导致付款后列表或详情不刷新的链路问题。

### 7.3 主项目修改与审核

1. 待审核、驳回状态允许编辑。
2. 审核页允许审核人修正指定字段后通过。
3. 已审核通过后的重大修改应走修改审批流程。
4. 修改审批至少记录：申请人、修改前内容、修改后内容、审核人、审核意见、审核时间。

### 7.4 子项目列表筛选

接口支持：

1. `mine=leader`：我负责的。
2. `mine=member`：我参与的。
3. `mine=all` 或缺省：按权限返回可见项目。

### 7.5 环节推进

1. 后端推进接口根据环节定义检查必传材料。
2. 采购环节根据采购类型检查供应商报价材料数量。
3. 验收环节根据普通验收或分步验收模式检查完成条件。
4. 推进失败返回结构化错误，包含缺失材料、当前状态、所需动作。

### 7.6 分步验收

1. `Phase` 增加或暴露 `is_stepped_acceptance`。
2. 验收步骤创建接口必须稳定可用，不允许 500。
3. `AcceptanceStep` 与上传文档通过 `acceptance_step_id` 关联。
4. 完成步骤前检查对应材料数量。
5. 验收环节推进前检查所有步骤均完成。

### 7.7 付款联动

1. 新增付款后重算子项目和主项目已用金额。
2. 红冲付款后重算子项目和主项目已用金额。
3. 金额重算应在同一事务中完成。
4. 若付款超预算，应保持现有确认或审批机制。

## 9. 问题清单到流程改造的映射

| 原问题 | 流程化归类 | 规格处理 |
| --- | --- | --- |
| 部门字段显示 UUID | 基础信息录入体验 | 部门下拉、部门名称展示、管理页显示 ID |
| 主项目缺少已用金额 | 金额联动 | 主项目实时汇总子项目付款金额 |
| 主项目缺少创建人和创建时间 | 状态可追溯 | 列表和详情展示创建信息 |
| 主项目没有修改审批 | 状态治理 | 已通过项目修改走审批 |
| 子项目创建流程不明确 | 流程引导 | 子项目创建页解释主项目前置和自动生成环节 |
| 金额联动未实现 | 财务闭环 | 付款和红冲后重算子项目、主项目金额 |
| 分步验收开关缺失 | 验收流程 | 验收环节支持普通和分步模式 |
| 分步验收步骤文档缺失 | 验收证据链 | 验收步骤关联材料 |
| 子项目列表缺少我的项目筛选 | 用户工作台 | 支持我负责、我参与筛选 |
| 环节详情缺少推进按钮 | 关口推进 | 满足条件显示推进按钮，不满足显示原因 |
| 新增验收步骤 500 | 后端稳定性 | 修复接口并补测试 |
| 采购类型缺少下拉和三价校验 | 采购关口 | 采购类型字段和询价类三价校验 |
| 附件显示系统文件名 | 材料可读性 | 显示 display_name |

## 10. 验收标准

### 10.1 主流程验收

使用 `docs/step by step.txt` 中的办公设备升级案例进行端到端测试：

1. 创建主项目并审核通过。
2. 创建工作站子项目并审核通过。
3. 审核通过后自动生成 6 大环节。
4. 上传立项材料并推进到采购。
5. 采购选择询价类，上传 3 家报价单后推进。
6. 上传合同后推进到验收。
7. 启用分步验收，创建两个验收步骤。
8. 每个验收步骤上传对应材料并完成。

## 16. Step-by-Step 闭环补充（2026-05-14）

`docs/step by step.txt` 已作为 V2 端到端验收剧本补齐闭环。本轮对 P0 规格做以下扩展：

1. 单人部门负责人可审核自己创建的主项目；多部门负责人环境仍禁止普通部门负责人自审。
2. 子项目成员可在自己参与的子项目中选择采购类型、上传材料并推进环节。
3. 付款环节和后评价环节均不再阻塞对方，但子项目最终完成仍要求 6 个环节全部完成。
4. 子项目完成后可在详情页结项。
5. 主项目在所有子项目完成、结项或中止后可在详情页结项。

这些扩展保持了“先流程、再模块”的方向：用户可以沿着主项目、子项目、环节、付款、后评价、结项的真实路径完成操作，而不是在多个孤立模块之间猜下一步。

补充验证口径：本轮已通过后端 `tests/unit` 全量、后端 `ruff/mypy/compileall`、前端 `lint/typecheck/test:unit/build`。后端全量 pytest 仅剩 Docker/Testcontainers e2e 因本机 `//./pipe/docker_engine` 不可用而无法启动，发布前需在 Docker 可用环境补跑。
