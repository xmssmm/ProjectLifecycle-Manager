## 0. 阅读说明

1. **本文档不是开发计划**，是路线图。每个 Phase 启动时需要：
   - 重新评估业务优先级（市场/用户反馈可能让某些 Phase 提前/取消）
   - 把当前 Phase 的任务按 DEVELOPMENT_PLAN 同样的细节度展开（Deliverable / DoD / 任务依赖）
   - 单独走一次 OPEN_QUESTIONS 决策流程
2. **任务 ID 规则**：`T-{phase}-{module}-{seq}`，与 MVP 体系一致（MVP 是 Phase 1，T-1-*）
3. **优先级标记**：
   - 🔥 高：MVP 用户最常抱怨 / 业务方点名要的
   - 🟡 中：明显有价值，但不影响生存
   - 🟢 低：锦上添花，按资源情况
4. **Phase 启动触发条件**：每个 Phase 有自己的"何时启动"信号，不要按时间硬启动
5. **预估工期**仅供初步规划，不构成承诺

## 2. Phase 2: 体验与可视化（~7 周）

### 2.1 启动触发条件

**满足任意一项即可启动**：
- MVP 上线 ≥ 1 个月，DAU 稳定（≥ 50% 注册用户每周登录 ≥ 1 次）
- 业务方明确提出"看不清整体进度"、"统计要手动算 Excel"等抱怨
- 综合部 / 财务部要求月度报表导出能力

### 2.2 任务清单

#### 模块 A：仪表盘（~2 周）

**T-2-DASH-01 仪表盘数据 API（按角色聚合）** 🔥
- Deliverable：`GET /api/v1/dashboard/{role-scope}` 系列接口
- 按角色返回不同数据集：

| 角色 | 关键指标 |
| --- | --- |
| `admin` | 全系统项目数、用户数、超预算项目数、即将到期任务数、各模块 API 错误率 |
| `dept_manager` | 全项目状态分布、本月新立项数、超预算项目列表、各部门项目数 |
| `finance_manager` | 本月付款总额、累计付款 vs 总预算、分子项目付款排行、待付款项目（无付款记录的子项目） |
| `proj_leader` | 我负责的子项目状态、我项目下到期/逾期任务数、待推进的环节、待审核的撤销 |
| `proj_member` | 我的待办任务数（按 due 日期）、参与的子项目最新动态 |

- DoD：
  - [ ] 单个仪表盘接口响应时间 ≤ 500ms（用 Redis 缓存 5 分钟）
  - [ ] 数据准确性：与底层表查询结果一致
  - [ ] 权限隔离：proj_leader 只能看自己的项目数据

**T-2-DASH-02 仪表盘前端页面** 🔥
- Deliverable：每个角色一个仪表盘页面，含图表（饼图、柱图、漏斗图）
- 库选型：Apache ECharts（与 Element Plus 兼容好）
- DoD：5 个角色各有定制仪表盘，加载时间 ≤ 2s

**T-2-DASH-03 项目进度漏斗** 🟡
- Deliverable：单个主项目内，所有子项目按 6 环节分布的漏斗视图
- 钻取：点击某环节看具体项目列表
- DoD：与子项目状态实时同步

#### 模块 B：报表导出（~1.5 周）

**T-2-REPORT-01 报表生成 service** 🔥
- Deliverable：
  - 后端 `app/services/report_service.py`
  - 支持的报表类型（按模板）：
    - `project_list`：项目清单（主项目 + 子项目展开）
    - `payment_journal`：付款流水（按时间/部门/项目筛选）
    - `dept_summary`：部门项目汇总（项目数、总预算、已付金额、完成率）
    - `monthly_summary`：月度统计
- 输出格式：Excel（openpyxl）+ PDF（reportlab 或 weasyprint）
- 异步生成：大报表用 Celery worker，结果存入 `report_jobs` 表
- DoD：
  - [ ] 4 种报表模板覆盖
  - [ ] 异步生成 + 进度查询接口
  - [ ] 大报表（≥ 1000 行）生成时间 ≤ 30s

**T-2-REPORT-02 报表下载与分享** 🟡
- Deliverable：`GET /api/v1/reports/{job_id}/download`
- 报表文件保留 7 天后自动清理（Celery 定时任务）
- DoD：权限校验：只有报表请求者能下载

#### 模块 C：移动端优化（~1.5 周）

**T-2-MOBILE-01 响应式布局适配** 🔥
- Deliverable：所有 MVP 已有页面在移动端（375px ~ 768px 宽度）可用
- 重点适配：
  - 项目列表 → 卡片式布局
  - 任务详情 → 单列布局
  - 文档预览（PDF）→ 全屏模式
  - 通知列表 → 优化触摸交互
- 不支持的页面：审核 / 付款 / 推进环节（移动端只读，引导切到 PC）
- DoD：iPhone Safari + Android Chrome 主流 2 个版本通过测试

**T-2-MOBILE-02 移动端任务完成快捷操作** 🔥
- Deliverable：移动端"我的任务"页面，单击即可完成任务（带二次确认）
- DoD：操作 ≤ 2 步完成任务

#### 模块 D：Office 文档预览（~1.5 周）

**T-2-DOC-04 OnlyOffice 集成（doc/xlsx/pptx 在线预览）** 🟡
- 背景：MVP 只支持 PDF 预览（OQ-05 = B），但用户最常上传的是 Word / Excel
- Deliverable：
  - Docker 部署 OnlyOffice Document Server（社区版免费）
  - 后端 `GET /api/v1/documents/{id}/preview-office`
  - 前端嵌入 OnlyOffice iframe
- 备选低成本方案：用 LibreOffice headless 把上传的 Office 文档转成 PDF 副本（牺牲编辑能力，换零 license 风险）
- 决策点：上线前需要在两者间确定（新 OQ-11）
- DoD：
  - [ ] doc/docx/xls/xlsx/ppt/pptx 都可预览
  - [ ] 与现有 PDF 预览（pdf.js）路由分离

#### 模块 E：通知增强（~1 周）

**T-2-NOTIF-04 通知偏好设置** 🟡
- Deliverable：用户可关闭某些场景的通知（白名单：所有 / 仅与我直接相关 / 自定义）
- 表：`user_notification_preferences(user_id, scenario, enabled)`
- DoD：偏好生效后立即对新通知起作用

**T-2-NOTIF-05 通知摘要（每日早 9 点汇总）** 🟢
- Deliverable：用户可选"实时通知"或"每日摘要"
- 摘要模式下，前一天的所有通知合并成一条
- DoD：摘要内容按场景分组、可折叠

## 3. Phase 3: 企业集成（~9 周）

### 3.1 启动触发条件

**满足任意一项即可启动**：
- 公司 IT 强制要求所有内部系统接入 SSO
- 用户反馈"忘了登录系统，错过审批" → 需要外部触达
- 安全合规审计要求所有上传文件主动扫描
- admin 转交 proj_leader 工作量过大（每月 ≥ 10 次手动转交）
- 其他系统（OA / ERP）需要消费本系统数据

### 3.2 任务清单

#### 模块 A：SSO 集成（~2.5 周）

**T-3-AUTH-01 OAuth2 通用适配层**
- Deliverable：抽象 `OAuthProvider` 接口，覆盖 authorize / callback / refresh / userinfo
- 数据库：`oauth_bindings(user_id, provider, external_id, refresh_token, ...)`
- DoD：接口可对接任何 OAuth2 提供方

**T-3-AUTH-02 至少一个具体提供方接入**
- 候选：企业微信 / 钉钉 / Azure AD / 自建 OAuth2
- 决策点：新 OQ
- 自动账号映射策略：
  - 选项 A：仅允许已有账号（admin 预先创建）通过 SSO 登录
  - 选项 B：首次 SSO 登录自动创建账号（默认 proj_member 角色，admin 可后续调整）
- DoD：完整登录 + 账号绑定 + 解绑流程

**T-3-AUTH-03 SSO 与本地账号共存**
- Deliverable：admin 可强制某用户必须 SSO（禁用密码）；可选 SSO（两者皆可）
- DoD：管理界面可切换策略

#### 模块 B：企业微信 / 钉钉 / 邮件 多通道通知（~2 周）

**T-3-NOTIF-01 通知通道抽象**
- Deliverable：`NotificationChannel` 接口（in_app / wework / dingtalk / email / sms）
- 用户偏好扩展：每个场景 × 每个通道独立开关
- DoD：MVP 现有通知逻辑不变，新通道按需触发

**T-3-NOTIF-02 企业微信适配** / **T-3-NOTIF-03 钉钉适配** / **T-3-NOTIF-04 SMTP 邮件适配**
- 各自独立任务
- 邮件模板系统（Jinja2）+ 退订机制
- DoD：每个通道至少跑通"任务到期"和"项目待审核"两个场景

**T-3-NOTIF-05 通知失败重试 + 死信队列**
- Deliverable：Celery 任务失败重试 3 次 + 进入死信队列告警 admin
- DoD：人为断网测试通过

#### 模块 C：病毒扫描升级（~1 周）

**T-3-DOC-01 ClamAV 主动扫描**
- 背景：MVP 只有黑名单拦截（OQ-06 = A），Phase 3 引入主动扫描
- Deliverable：
  - Docker 部署 clamav daemon
  - 上传后异步扫描（不阻塞响应）
  - 扫描结果：`pending` / `clean` / `infected`，infected 文件隔离 + 通知 uploader + admin
- DoD：
  - [ ] 标准 EICAR 测试文件被检出
  - [ ] 病毒库每日自动更新
  - [ ] 扫描期间文件状态显式（前端展示"扫描中"标志）

#### 模块 D：proj_leader 自助转交（~1 周）

**T-3-USER-01 升级转交流程为 OQ-09 选项 E**
- 背景：MVP 只有 admin 手动（OQ-09 = A）
- Deliverable：
  - 原 proj_leader 主动发起转交 → 候选人确认 → dept_manager 审核 → 生效
  - admin 兜底通道保留（离职等场景）
- DoD：
  - [ ] 完整流程跑通
  - [ ] admin 兜底场景：候选人未确认超过 7 天 admin 可强制转交

#### 模块 E：开放 API（~2.5 周）

**T-3-API-01 API Key 管理**
- Deliverable：admin 可为外部系统签发 API Key + 权限范围
- 表：`api_keys(key_hash, name, permissions, created_by, expires_at, last_used_at)`
- DoD：API Key 失效后立即拒绝

**T-3-API-02 公开 Read-only API**
- Deliverable：`/api/external/v1/*` 系列接口，可读取项目、付款、文档元数据
- 限流：API Key 维度，默认 1000 次/小时
- 文档：自动生成 OpenAPI + 调用示例
- DoD：
  - [ ] 第三方系统（如 OA）可消费
  - [ ] 限流生效

**T-3-API-03 Webhook 推送**
- Deliverable：可订阅事件（项目状态变更、付款发生、环节推进等），HTTP POST 推送到外部
- 重试机制：失败重试 5 次（指数退避）+ 死信队列
- DoD：admin 可配置 webhook URL + secret（HMAC 签名）

## 4. Phase 4: 规模与合规（~7 周）

### 4.1 启动触发条件

- 数据库主表（main_projects / sub_projects）行数超过 10 万
- 单表查询性能下降到不可接受（P99 > 2s）
- 海外分公司用户超过总用户 10%
- 合规审计要求文档全文检索能力
- 业务方需要批量录入历史项目

### 4.2 任务清单

#### 模块 A：数据归档与冷热分离（~2 周）

**T-4-DATA-01 归档策略与 archive 表**
- 背景：OQ-03 = A 永久保留，但永久 ≠ 都在主库
- Deliverable：
  - 已结项 ≥ 2 年的主项目及其下属数据迁移到 `archive_*` 系列表
  - 同库不同表（避免 DB 切换复杂度），定期可迁移到独立 archive DB
  - 用户查询自动 union（or 显式查归档库）
- DoD：归档后主库性能提升可量化

**T-4-DATA-02 归档/恢复操作面板**
- Deliverable：admin 可手动归档某主项目；可恢复到主库
- DoD：归档/恢复全程审计

#### 模块 B：多时区支持（~1.5 周）

**T-4-I18N-01 用户时区字段**
- 背景：OQ-10 = A 单时区
- Deliverable：
  - `users.timezone` 字段（默认 `Asia/Shanghai`）
  - 前端显示自动转换为用户时区
  - 数据库存储仍为 UTC
- DoD：跨时区用户看到的时间正确

**T-4-I18N-02 Celery beat 多时区调度**
- Deliverable：原本固定 09:00 推送，改为按用户时区分组调度
- DoD：每个用户在其本地 09:00 收到通知

**T-4-I18N-03 中英文国际化（可选）** 🟢
- Deliverable：vue-i18n 集成，UI 文案抽离到资源文件
- DoD：英文版完整可用

#### 模块 C：高可用与性能（~2 周）

**T-4-PERF-01 PostgreSQL 主从复制**
- Deliverable：主从架构，读写分离
- 配置：报表 / 仪表盘等读密集走从库
- DoD：主库故障时，从库可提升为主，业务中断 ≤ 5 分钟

**T-4-PERF-02 Redis Sentinel / Cluster**
- Deliverable：Redis 高可用部署
- DoD：单实例故障不影响业务

**T-4-PERF-03 应用层水平扩展**
- Deliverable：FastAPI 多副本部署 + 健康检查
- DoD：50 并发提升到 ≥ 200 并发

**T-4-PERF-04 关键查询性能优化**
- Deliverable：识别慢查询 + 加索引 + 物化视图
- DoD：所有 P99 ≤ 800ms

#### 模块 D：全文检索（~1 周）

**T-4-SEARCH-01 文档全文索引**
- Deliverable：
  - 上传文档异步抽取文本（pdf 用 pdfminer，office 用 textract，扫描件用 OCR）
  - 索引到 PostgreSQL FTS 或 OpenSearch（TBD）
  - `GET /api/v1/search?q=...&scope=documents` 接口
- DoD：上传后 5 分钟内可被搜到

#### 模块 E：批量导入导出（~0.5 周）

**T-4-DATA-03 项目批量导入**
- Deliverable：Excel 模板 + 批量导入接口
- 校验：失败行不影响成功行；返回详细错误清单
- DoD：1000 行项目 ≤ 60s 导入完成

**T-4-DATA-04 数据库全量导出**
- Deliverable：admin 可一次性导出全库为 Excel/CSV 包
- DoD：含完整外键引用，可独立审计

## 5. Phase 5: 平台化与智能化（TBD）

### 5.1 触发条件

- 业务方需要支持非采购类项目（科研、合规、人力等）
- 报表需求多样化，开发追不过来
- 数据量足够支撑数据驱动的决策

### 5.2 候选方向（仅作前瞻参考，不做详细任务拆分）

#### 5.2.1 工作流引擎自定义 🟡

**目标**：突破 6 环节硬编码，支持自定义项目类型 / 环节流。

**核心能力**：
- 项目类型管理：admin 可定义新的项目类型（如"科研项目""合规项目"）
- 环节模板编辑：每个项目类型可定义自己的环节集合 + 顺序依赖 + 必传文档
- 流程版本控制：模板修改不影响进行中的项目

**实现复杂度**：高。这本质上是引入 BPMN 思想，需要重构 phase / phase_doc_template 体系。

**预估工期**：6-8 周

#### 5.2.2 自定义报表 🟡

**目标**：业务方自助拖拽生成报表，不依赖开发。

**核心能力**：
- 数据集定义（基于现有表的视图）
- 字段拖拽 + 筛选 + 聚合
- 图表类型选择
- 定时报表（每月 1 号自动生成 + 邮件）

**实现路径**：
- 选项 A：自研轻量报表设计器（成本高，灵活）
- 选项 B：嵌入开源 BI 工具（如 Metabase、Superset）

**预估工期**：4-6 周

#### 5.2.3 多项目类型与跨项目协作 🟢

**目标**：当系统沉淀的项目数据足够多，支持跨项目分析（比如"同类项目历史平均工期"）。

**核心能力**：
- 项目标签 / 分类
- 跨项目对标分析
- 项目模板库（新建项目可基于历史模板）

#### 5.2.4 AI 辅助功能 🟢（探索性）

⚠️ 引入 AI 前需评估数据隐私 / 模型选型 / 成本。

**候选场景**：
- **异常检测**：识别可能延期 / 超预算的项目（基于历史数据训练）
- **智能催办**：基于用户响应模式优化通知时机
- **文档自动分类**：上传文档时建议 doc_type
- **风险预警**：综合多维度信号给出"项目健康度"评分
- **智能问答**：基于本系统数据回答"我们部门去年办了多少个项目""平均周期多少"

**实现路径**：
- 早期：调用外部大模型 API（OpenAI / Claude / 国产模型）+ RAG
- 后期：如数据敏感，考虑私有化部署

**预估工期**：每个场景独立评估，2-6 周不等

## 6. 风险与依赖

### 6.1 各 Phase 共同风险

| 风险 | 缓解 |
| --- | --- |
| MVP 出现重大架构问题需要返工 | Phase 2 启动前做一次架构评审 |
| 业务方需求变更，原 Phase 优先级失效 | 每 Phase 启动前重新走 OPEN_QUESTIONS 流程 |
| 团队人员变动 | 每 Phase 工期预留 20% buffer |
| 第三方依赖 license / 价格变化（OnlyOffice / OAuth 提供方 / SMS 服务等） | 关键集成保留 2 个备选方案 |

### 6.2 Phase 间依赖关系

- Phase 2 → Phase 3：仪表盘和报表如果先做，Phase 3 的 webhook 才能推送有意义的数据
- Phase 3 SSO → Phase 5 平台化：账号体系打通是平台化前提
- Phase 4 性能优化 → Phase 5 全部：扩展性是规模化前提

### 6.3 可以并行的工作

- Phase 2 仪表盘 + 报表 可并行（不同模块）
- Phase 3 SSO + 多通道通知 可并行
- Phase 4 各模块基本独立，可全并行

## 8. 给业务方 / PM 的备忘

### 8.1 何时该启动下一个 Phase

不是按时间启动，而是按 **痛点信号**：

| 痛点信号 | 对应 Phase 模块 |
| --- | --- |
| "我看不到全公司项目情况" / "做汇报要手动算 Excel" | Phase 2 仪表盘 + 报表 |
| "在外面想批一下却必须开电脑" | Phase 2 移动端 |
| "总是忘记登录系统" / "重要事情没收到提醒" | Phase 3 多通道通知 |
| "公司其他系统都 SSO 了，就这个还要单独密码" | Phase 3 SSO |
| "项目数据想给 ERP 用" | Phase 3 开放 API |
| "查询慢了" / "数据库越来越大" | Phase 4 归档 + 性能 |
| "我们想用同样的系统管理科研项目" | Phase 5 工作流自定义 |
| "想让 AI 帮我们看看哪些项目有风险" | Phase 5 AI |

### 8.2 何时该停下来重新评估

每个 Phase 启动前 + Phase 进行到 50% 时，问以下问题：
1. MVP / 已交付部分的实际使用率如何？
2. 用户最常抱怨的事情是不是在我们计划里？
3. 业务/政策环境是否有变化？（如新合规要求）
4. 计划中某些 Phase 是否已经不再需要？
5. 是否有新的迫切需求需要插队？

如果答案显示当前路线图偏离实际需求，**不要硬推**，重新评估并调整。
